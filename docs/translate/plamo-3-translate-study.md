2026-11-05 調査・**同日実測済み（Phase 0 完了）**。
→ [README.md](../../README.md) / [CLAUDE.md](../../CLAUDE.md) / [docs/](../README.md)

当初は公開情報からの見積もりだけだったが、**同日に実機で測って裏を取った**。
見積もりだった箇所は実測値に差し替え、**見積もりと実測のずれも残してある**（§4）。

## 結論

**できる。実機で動かして確認した。** ただし
**「翻訳」は易しく、「レイアウトを保つ」が仕事の本体**で、
**Intel の Vulkan には必ず踏む罠が 1 つある**（§3.4）。

| | 結果 |
|---|---|
| **このマシンで動くか** | **動いた。** ビルド不要（Vulkan ビルド済み zip 36 MB を展開するだけ）。`plamo3` は 2025-12-28 に本家へマージ済み |
| **速度** | **0.8b = 123 tok/s / 2b = 36〜45 tok/s**（実測）。8b は載る、**31b は載らない**（§4） |
| **実用になるか** | **なった。** 実際の README（645 行）を**0.8b で 51 秒 / 2b で 177 秒**で全訳（§4.2） |
| **翻訳品質** | **良い。** 技術文書として自然。**2b は明確に 0.8b より上**（§4.4） |
| **レイアウト保持** | **分割方式で完全に保てた。** コードフェンス 6/6、見出し 22/22、URL 21/21、インラインコード **2b では 132/132 保存**（§4.3） |
| **【重要】Intel Vulkan の罠** | 素で動かすと **GPU が落ちてサーバがクラッシュする**。`GGML_VK_DISABLE_COOPMAT=1` で解決し、**この用途では速度の代償がほぼ無い**（§3.4） |
| **工数感** | 最小構成（リージョン翻訳を別バッファに出す）で Elisp 200〜300 行。markdown 構造対応と help 対応はその先 |

**モデルには構造保持を頼めない**（PFML3 に指示文の欄が無い。§6）が、
**頼む必要が無かった**——分割して渡せば、記法は向こうが勝手に素通しする（§4.3）。

**用途ごとの見立てはかなり違う。**

| 用途 | 見立て | 理由 |
|---|---|---|
| **ソースコメントの翻訳** | **最も easy。ここから入るべき** | tree-sitter で `(comment)` ノードを正確に取れる。この設定は既に tree-sitter 前提（[docs](../languages/tree-sitter.md)）。構造が壊れる余地がそもそも小さい |

| **`describe-function` / `describe-mode`** | **できる。ただし「元のバッファを書き換えない」のが条件**（§6.2） | help バッファはボタンとテキストプロパティの集合体。本文を訳文で差し替えるとリンクが全滅する |

## 1. 検証環境（このマシンの実測）

2026-11-05 に `Get-CimInstance` で取得。

| | |
|---|---|
| OS | Windows 11 Pro 10.0.26300 |
| CPU | Intel Core Ultra 5 228V（Lunar Lake、8 コア / 8 スレッド） |
| iGPU | Intel Arc 130V（Xe2、7 コア）。ドライバ 32.0.101.8724 |
| NPU | Intel AI Boost（デバイスとして存在を確認） |
| メモリ | **31.52 GB**（LPDDR5X-8533 × 8、オンパッケージ） |
| 空きディスク | C: 102.8 GB |
| Python | 3.15.2（scoop）/ uv 0.13.7 |
| 既に無いもの | **ollama / llama.cpp / cmake / ninja はいずれも未導入** |

### 【重要】GPU 名の "(16GB)" は SKU の表示文字列で、容量の上限ではない

ドライバは `Intel(R) Arc(TM) 130V GPU (16GB)` と名乗り、`Win32_VideoController`
の `AdapterRAM` は 2 GB を返す。**どちらも実際に使える量ではない。**
Lunar Lake の iGPU はオンパッケージメモリを CPU と共有するので、**効く制約は
「31.5 GB の共有プール」**の方。`AdapterRAM` が 32bit で飽和しているだけなので、
**この値を見てモデルサイズを決めてはいけない。**

**実測での正解は `llama-cli --list-devices`。**

```
Vulkan0: Intel(R) Arc(TM) 130V GPU (16GB) (18399 MiB, 17631 MiB free)
```

**GPU から使えるのは約 17.2 GB**（名前の "16GB" でも `AdapterRAM` の 2 GB でもない）。
積載可否はこの値で判断する（§4.1）。

### 帯域（計算値）

LPDDR5X-8533、Lunar Lake のバス幅 128 bit なので

```
8533 MT/s × 128 bit ÷ 8 = 136.5 GB/s
```

**トークン生成の速度はほぼこれだけで決まる**（§4）。

## 2. 公開形態の事実

2026-11-05 に Hugging Face の API とモデルカードから取得。

### サイズと量子化

4 サイズ（0.8b / 2b / 8b / 31b）× 7 形式（BF16 / FP8 / W4A16 / W4AFP8 / NVFP4 /
**GGUF** / MLX-4bit）。量子化は AutoRound。

**GGUF は pfnet 公式から出ている**（`pfnet/plamo-3-translate-{size}-GGUF`）。
API でファイル一覧を引いた実サイズ:

| | Q2_K | Q3_K_M | Q4_0 | Q4_K_M |
|---|---|---|---|---|
| 0.8b | 0.38 | 0.45 | 0.51 | **0.53** |
| 2b | 1.14 | 1.39 | 1.58 | **1.68** |
| 8b | 3.21 | 4.01 | — | **4.92** |
| 31b | 12.61\* | 15.86\* | — | **19.53\*** |

単位 GB。`*` は未照会でモデルカードの表の値。**8b と 31b に Q4_0 は無い。**

- モデルカードは **Q2_K の精度低下**を明記している（0.8B で最大 3.29 ポイント）。
  **Q2_K は選ばない。** 既定は Q4_K_M
- GGUF の推奨実行環境は「CPU や各種 GPU、llama.cpp、CPU と GPU の併用可」。
  **NVIDIA を要求していないのはこの形式だけ**（FP8 / W4A16 / NVFP4 は全部 NVIDIA 指定）

### 対応言語

53 言語（HF 表示は中国語を 1 つに畳んで 52）。コードは `ja` / `en` / `zh-hans` /
`zh-hant` など小文字。`ja(easy)`（やさしい日本語）という特殊値がある。

### コンテキスト長

学習時の最大長が**入力と出力の合計で 32,768 トークン**。超える場合は分割が必要
（モデルカードに明記）。**README 1 本なら余裕で収まるが、どうせ分割するので
実質的な制約にならない。**

### 【重要】プロンプト形式は PFML3 という独自プロトコルで、自由文の指示欄が無い

これが §6 の結論を決めている。書式は特殊トークンによる構造化:

```
<|plamo:tag|>dataset<|plamo:msg|>translation<|plamo:tag|>input<|plamo:msg|>The meeting has been rescheduled to next Monday.<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>ja<|plamo:msg|>
```

最後の `<|plamo:msg|>` の直後から訳文が生成され、`<|plamo:tag|>` または
`<|plamo:bos|>` の出力で止まる（= stop シーケンスはこの 2 つ）。

**渡せるものは次の 5 つだけ。** システムプロンプトも指示文も存在しない。

| 要素 | 書式 | 用途 |
|---|---|---|
| `target_lang` | `<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>ja` | 必須 |
| `source_lang` | `<|plamo:tag|>input<|plamo:key|>lang<|plamo:val|>en` | 省略可（自動判定） |
| `context` | `<|plamo:tag|>context<|plamo:msg|>...` | 周辺文脈。`dataset` の直後に置く |
| `glossary` | `<|plamo:tag|>glossary<|plamo:index|>dashboard<|plamo:item|>管理画面` | 用語集。今回の `input` の直前 |
| `form` | `<|plamo:key|>form<|plamo:val|>plain\|polite` | 常体 / 敬体。`ja` のみ |

対訳履歴（過去の input/output ペア）を並べて一貫性を上げることもできる。
**履歴は自動保存されないので毎回こちらで積む。**

公式 GGUF リポジトリには `chat_template.jinja` が**別ファイルとして同梱**されている
（取得して読んだ）。`llama-server --jinja --chat-template-file` に渡せば
`/v1/chat/completions` + `chat_template_kwargs` で上の 5 つを指定できる。
テンプレートは入力の検証もしていて、**本文に `<|plamo:` が含まれていたら
`raise_exception` で弾く**（プレースホルダにこのトークン類を使えないという意味。§6.1）。

### ライセンス（→ 条文を読んだ結果は §7）

PLaMo コミュニティライセンス契約。`license: other` /
`license_name: plamo-community-license`。**費用は発生しない**（§7.1）。

## 3. 実行方式の比較

| 方式 | このマシンで | 判定 |
|---|---|---|
| **`llama-server` を直接叩く** | Windows の Vulkan ビルド済み zip が 35.9 MB。展開だけ | **採用候補。これが本命** |
| `plamo-translate-cli`（PFN 公式） | README のインストール節が **"For macOS" のみ**。既定バックエンドは MLX（Apple Silicon 専用） | **使わない**（§3.1） |
| Ollama | 未導入。GGUF の取り込みは可能だが、同梱 llama.cpp の世代とテンプレート層が増える | 不要。llama-server の方が制御できる |
| Transformers / vLLM | BF16 は 5.76 GB（2b）、`trust_remote_code=True` 必須。vLLM は実質 NVIDIA | **不適** |
| OpenVINO バックエンド | `llama-b12125-bin-win-openvino-2026.4.1-x64.zip` が存在。NPU を使える可能性 | **将来の選択肢**。最初の一手にはしない |

### 3.1 PFN 公式 CLI を使わない理由

README を読んだ事実:

- インストール手順が macOS 前提。**Windows への言及が無い**
- 既定バックエンドが MLX = Apple Silicon 専用。llama.cpp バックエンドも
  `llama-server` b11960 (0.8.0) 以降を**別途用意する前提**
- 常駐モードは **MCP サーバ**（`http://localhost:8000/mcp`）。
  Emacs から MCP を話すのは遠回り
- **用語集・文脈・敬体/常体を渡すオプションが README に無い。**
  モデルの持つ機能を CLI が塞いでいる
- llama.cpp 経路では**プロンプトキャッシュを使わない**と明記

つまり CLI は「`llama-server` を起こして MCP で包む」層で、こちらが欲しいのは
その下の `llama-server` そのもの。**層を 1 つ減らした方が、速く・細かく・
Windows で動く。** CLI から借りるのは既定値の知識だけでよい。

### 3.2 採る形

```
Emacs ──HTTP(localhost)──> llama-server.exe ──Vulkan──> Arc 130V
         url.el / 非同期         常駐・モデル常駐
```

llama.cpp は b12125（2026-11-05 公開）時点で Windows 向けに
`llama-b*-bin-win-vulkan-x64.zip`（35.9 MB）/ `-sycl-x64.zip`（148.8 MB）/
`-openvino-*.zip`（99.9 MB）を配布している。**cmake も Visual Studio も要らない。**

- **Vulkan から試す。** 36 MB で依存はドライバだけ。Arc では SYCL より速い例が
  複数報告されている
- SYCL は oneAPI 層が入るぶん重く、Arc では Vulkan に負ける報告がある
  （[llama.cpp #26010](https://github.com/ggml-org/llama.cpp/issues/26010)）。
  **両方測って決める**

### 3.3 エンドポイントは `/completion`（生プロンプト）を本線にする

`/v1/chat/completions` + `--jinja` でも動くはずだが、**PFML3 を自分で組み立てて
`/completion` に渡す形を本線にする。**

- Jinja テンプレートの解釈、`chat_template_kwargs` の受け渡し、llama.cpp 側の
  テンプレート実装の世代差——**壊れうる層が 3 つ増える**
- PFML3 は文字列連結だけで組める。§2 の表がそのまま仕様になる
- `glossary` を**動的に組み替える**のが §6 の肝なので、こちら側で持つ方が素直

`stop` に `["<|plamo:tag|>", "<|plamo:bos|>"]` を渡す。

**実測で確認済み:** `/completion` は `prompt` 中の `<|plamo:...|>` を
**特殊トークンとして正しく解釈する。** 文字列をそのまま渡すだけでよく、
`/tokenize` でトークン ID 列を作る必要は無かった。

なお **`stop` は実際には発火しない。** モデルが訳文の最後で EOS を出すので、
全リクエストが `stop_type: "eos"` で終わった。**保険として渡しておく。**

### 3.4 【重要】Intel の Vulkan は `coopmat` を切らないとクラッシュする

**素の設定では GPU が落ちてサーバが死ぬ。** 実測で 3 回再現した。

```
ggml_vulkan: device lost on Vulkan0
ggml_vulkan: getFenceStatus at ggml-vulkan.cpp:355
slot iterate: got exception: vk::Device::getFenceStatus: ErrorDeviceLost
GGML_ASSERT(batch.slot_batched || batch.size() == 0) failed
[exited with code 9]
```

**症状の形。**

- 生成中に **GPU が 17〜23 秒ハング**し、`device lost` のあと
  **アサーション失敗でプロセスごと落ちる**（終了コード 9）
- **落ちるまでの時間が毎回違う**（175 秒 / 26 秒 / 34 秒）。
  入力にも回数にも相関しない
- **Windows のイベントログに 4101（ディスプレイドライバの応答停止）は出ない。**
  TDR の設定も既定のまま。**OS 側には何の痕跡も残らない**
- `-b` / `-ub` を小さくしても、`--parallel 1` にしても直らない
- **最初は「暴走生成」だと誤診した。** ハング時間 17 秒が
  `n_predict` 2048 を 120 tok/s で生成しきる時間（17.1 秒）とほぼ一致したため。
  入力長に比例した上限を入れても落ちたので、**偶然の一致だった**

**対策は環境変数 1 つ。**

```sh
GGML_VK_DISABLE_COOPMAT=1
```

llama.cpp は起動時に `matrix cores: KHR_coopmat` を使うと報告する。
**この協調行列（matrix core）経路が Intel のドライバで壊れている。**
切ると**完走する**（README 翻訳 4 回・**207 秒連続稼働で失敗 0**。
最初のクラッシュが 175 秒だったので、それを超えて無事）。

**【重要】この用途では速度の代償がほぼ無い。**

| | pp512 | tg128 |
|---|---|---|
| coopmat **有効**（既定） | **5092 tok/s** | 121.5 tok/s |
| coopmat **無効**（対策後） | 2178 tok/s | **123.5 tok/s** |
| CPU のみ（`-ngl 0`） | 770 tok/s | 81.2 tok/s |

プロンプト処理は 57% 落ちるが、**生成は落ちない**（誤差の範囲で、むしろ速い）。
翻訳は生成律速（§4.2 で入力 12242 トークンに対し生成 4885 トークン、
それでも入力側の所要は無視できる）なので、**実質タダで安定が買える。**

- **CPU のみでも 81 tok/s 出る**ので、GPU が駄目な環境の逃げ道になる
- 未検証: ドライバ更新（32.0.101.8724）で直るか、SYCL / OpenVINO では起きないか

## 4. 実測（2026-11-05、Phase 0）

測定条件は §1 のマシン、llama.cpp **b12125** Vulkan ビルド済みバイナリ、
`GGML_VK_DISABLE_COOPMAT=1`、`-ngl 99 -c 4096 --parallel 1 -b 512 -ub 256`、
`temperature 0`。モデルは pfnet 公式 GGUF の Q4_K_M。

### 4.1 素の速度（`llama-bench`）

| モデル | ファイル | params | pp512 | tg128 |
|---|---|---|---|---|
| **0.8b** | 0.53 GB | 890 M | 2178 tok/s | **123.5 ± 3.0 tok/s** |
| **2b** | 1.68 GB | 2.88 B | 613 tok/s | **36.0 ± 4.1 tok/s** |

`llama-cli --list-devices` の実測値:

```
Vulkan0: Intel(R) Arc(TM) 130V GPU (16GB) (18399 MiB, 17631 MiB free)
```

**GPU から使えるのは約 17.2 GB。** これで積載可否が確定する。

| | Q4_K_M | 載るか |
|---|---|---|
| 0.8b / 2b / **8b** | 0.53 / 1.68 / **4.92 GB** | **載る**（8b も余裕） |
| **31b** | **19.53 GB** | **載らない**（17.6 GB を超える）。検討から外す |

### 4.2 見積もりと実測のずれ

| | 当初の見積もり | 実測 | |
|---|---|---|---|
| 0.8b 生成 | 80〜140 tok/s | **123.5** | **的中** |
| 2b 生成 | 30〜45 tok/s | **36.0** | **的中** |
| 2b プロンプト処理 | 1000〜2000 tok/s | **613** | **外した**（2〜3 倍の楽観） |
| 0.8b プロンプト処理 | — | 2178（coopmat 有効なら **5092**） | — |

**帯域律速の計算（§当初の 53% 効率）は生成速度によく当たった。**
外したのはプロンプト処理で、しかも coopmat の有無で 2 倍以上動くので
**そもそも 1 つの数字で語れない量**だった。

### 4.3 実際の README を全訳した（end-to-end）

題材は `straight/repos/dired-hacks/README.md`（**645 行 / 26.8 KB**、
英語、コードブロック・見出し・リンク・バッジ・表を含む実物）。
§6.1 の分割方式を試作して段落単位に投げた（`tmp/plamo-probe/segment.ps1`）。

| | 0.8b | 2b |
|---|---|---|
| **所要** | **51.3 秒** | **176.8 秒** |
| 翻訳した単位 | 132 | 132 |
| 素通しした単位 | 56 | 56 |
| 生成トークン | 4885 | 4909 |
| 入力トークン | 12242 | 12242 |
| 平均生成速度 | 95.2 tok/s | 27.8 tok/s |
| **1 単位あたり** | **389 ms** | **1339 ms** |

**構造の保持（入力 / 出力で一致すべき値）。**

| | 0.8b | 2b |
|---|---|---|
| コードフェンス | **6 / 6** | **6 / 6** |
| 見出し | **22 / 22** | **22 / 22** |
| 表の行 | **1 / 1** | **1 / 1** |
| **URL（21 種）** | **消失 0** | **消失 0** |
| **インラインコード（132 種）** | 消失 **1** | **消失 0** |
| 生成上限で打ち切られた単位 | 0 | 0 |
| 通信失敗 | 0 | 0 |

**分割方式は意図どおり機能した。** コードブロックも URL も壊れない。

0.8b が落とした 1 件は `` `dired+` `` で、
**バッククォートを日本語の「」に置き換えた**（`これを単なる「dired+」にしない`）。
2b は `` `dired+` `` のまま保った。

**モデルに頼めないはずの構造保持が、実際には勝手に守られた。** §6 の
「glossary に恒等写像を積む」策は**要らなかった**（実測で、有無による差が無い）。
ただし 0.8b で 1 件外したので、**検証は必要**（§4.5）。

### 4.4 訳質（0.8b と 2b の比較）

同じ段落。原文は
`Collection of useful dired additions. I don't want this to become another `dired+`, so I'm splitting ...`

| | 訳文 |
|---|---|
| **0.8b** | 便利なdired追加機能のコレクション。これを単なる**「dired+」**にしないため、すべての機能を互いに独立した個別のパッケージに分割する。 |
| **2b** | 便利なdired拡張機能のコレクション**だ**。これが**また別の**`dired+`になるのは避けたいので、すべての機能を互いに独立した個別のパッケージに分割する。 |

**2b のほうが明確に良い。** 0.8b は `another`（また別の）を落とし、
バッククォートも壊した。**どちらも技術文書として読める水準**で、
用語の訳し方（dired 追加機能 / dired 拡張機能）も妥当。

### 4.5 【重要】実測で見つかった、訳文の側の問題 3 つ

どれも**モデルの不具合ではなく、こちらの設計で面倒を見る必要がある**もの。

#### (1) 見出しを訳すと目次のアンカーが壊れる

README 先頭の目次は `* [Contribute!](#contribute)` の形で、
**見出しの英語テキストから生成されたアンカー**を指す。試作は
目次行を「単独のリンクだから訳さない」と判定して素通しし（これは正しい）、
**見出しだけを `# 貢献しよう！` に訳した。** 結果、
**目次のリンクが全部外れた。**

選択肢は 3 つ。**(c) を推す。**

| | 手 | 評価 |
|---|---|---|
| a | 見出しを訳さない | 読みやすさを大きく損なう |
| b | 目次も訳してアンカーを張り替える | 正しいが、アンカーの生成規則（GFM の正規化）を自前で再現することになる |
| c | **見出しに原文を併記**（`# 貢献しよう！ (Contribute!)`） | アンカーは GFM の規則で原文側から作られるので**リンクが生きる**。しかも原語が分かって都合がよい |

#### (2) `form=plain` は段落ごとに守られないことがある

`form=plain`（常体）を全段落に渡したのに、**出力は常体と敬体が混ざった**
（「行える」「含まれている」の中に「提案してください」「できます」）。
**`form` は指示ではなくヒント**と考えるべき。

文書全体の文体を揃えたいなら、**対訳履歴（§6.4）を積むか、
訳し終わったあとに文末を機械的に揃える**ほうが確実。

#### (3) 検証コードを書くときに踏んだ罠（実装時も踏む）

識別子が訳文に残ったかを数える検証を書いたら、
**132 件すべて「消失」と報告された**（実際の消失は 1 件）。
原因は PowerShell の `-like` が**バッククォートをエスケープ文字として解釈する**
ため、`` `add-to-list` `` というパターンが壊れていた。
`String.Contains` に変えたら正しく 1 件になった。

**教訓は Elisp でも同じ。** 検証の比較は
**正規表現やワイルドカードを通さず、素の文字列一致で行う**
（`string-search`。`string-match` は不可）。
**検証器が壊れていると「全部壊れている」と報告されるので、
真の壊れ 1 件が埋もれる。**

### 4.6 対話用途のレイテンシ（`describe-function` 相当）

実際の docstring に似せた英文 3 本を 1 リクエストで訳した実測。

| 入力 | 0.8b | 2b |
|---|---|---|
| 短い docstring（60 語 → 52 tok） | **0.46 秒** | **1.39 秒** |
| 中くらい（140 語 → 123 tok） | **1.09 秒** | **3.06 秒** |
| 長い（260 語 → 188 tok） | **1.59 秒** | **4.59 秒** |

**当初の見積もり（0.8b で 2〜3 秒、2b で 6〜8 秒）より速かった。**
docstring は思ったより短く、出力が 250 トークンに達しないため。

- **`describe-function` は 0.8b なら体感即時**（1.6 秒以内）
- **2b でも使える**（長いもので 4.6 秒）。逐次表示があれば十分
- **0.8b を対話用・2b を文書用に 2 本常駐させるのが現実的。**
  メモリは 0.53 + 1.68 = 2.2 GB で、17.6 GB の GPU 予算に対して何でもない
  （実際にポート 18080 / 18081 で同時に動かして測った）

### 4.7 【重要】段落ごとに分けるので、トークン単位の逐次表示は要らない

§6 の結論により、翻訳は**段落単位の多数の小リクエスト**になる。
実測の **1 単位あたり 389 ms（0.8b）/ 1339 ms（2b）** がその粒度。

- **段落が訳し終わるたびにバッファへ挿入すれば、それが進捗表示になる**
- つまり **SSE ストリーミングを実装しなくてよい。** `url-retrieve` の
  非同期コールバックで足りる（`my-htnblog` と同じ作り）

`my-claude` がやっているような process filter での逐次パースは不要。
**これは工数をかなり下げる判断。**

## 5. Emacs 側の実装方針 — この設定固有の罠

CLAUDE.md に既に書かれている事実から、設計が決まる部分。

### 5.1 【重要】リクエストごとにプロセスを起こしてはいけない

Windows の Emacs は `call-process` のプロセス生成だけで **59〜76 ms** 払う
（CLAUDE.md「Windows 固有」）。段落ごとに `plamo-translate` を叩く形にすると、
**README 1 本で数十回、翻訳と無関係なオーバーヘッドだけで数秒**積む。

→ **`llama-server` を常駐させ、HTTP で話す。** モデルのロード（1.7 GB で
数秒）も 1 回で済む。この設定が `gitd/` で常駐プロセスに寄せたのと同じ理屈。

### 5.2 【重要】`url-request-data` は unibyte にする

`my-htnblog` が踏んだ罠がそのまま当てはまる（CLAUDE.md / [docs](../htnblog/my-htnblog.md)）。
JSON ボディは `encode-coding-string ... 'utf-8` を通してから渡す。
**url.el はプロセスを通らないので `default-process-coding-system` では直らない。**
応答側も明示的に utf-8 で decode する。

日本語を扱う機能で文字化けは「エラーを出さず静かに」起こるので、
ここは最初から正しく書く。

### 5.3 サーバの寿命

- 初回利用時に遅延起動（`start-process`）。**起動で Emacs を止めない**
- モデルのロード中に来たリクエストは保留する。
  SQLcl で踏んだ「プロンプトより前に送ると二度と応えない」と同種の問題を
  作らないよう、**準備完了を確認してから流す**（[docs](../languages/sqlcl.md)）
- `kill-emacs-hook` で落とす。ポートは defcustom
- **モデルを切り替えるには再起動が必要**（llama-server の仕様）。
  0.8b と 2b を使い分けたいなら **2 本立てる**か、切り替えコマンドを用意する。
  メモリは 0.53 + 1.68 = 2.2 GB なので 2 本常駐も現実的

### 5.4 絶対に元ファイルを書き換えない

用途が「clone してきた他人のリポジトリを読む」なので、**既定では翻訳結果を
ファイルに書かない。** 別バッファか overlay で見せる。

## 6. 本題 — レイアウトを壊さないために

### 【重要】モデルに「構造を保て」と頼む経路が存在しない

PFML3 には指示文の欄が無い（§2）。渡せるのは `target_lang` / `source_lang` /
`context` / `glossary` / `form` の 5 つだけ。つまり

> 「コードブロックはそのまま残して」「markdown の記法を壊さないで」

と**頼む場所が無い**。汎用 LLM（`my-claude` 経由の Claude など）との最大の違いは
品質ではなくここ。

**したがって構造の保持は、プロンプトの工夫ではなく Emacs 側の分割で
「構造的に保証」する。** 訳させるのは散文だけにして、記法・識別子・URL は
**そもそもモデルに渡さない。**

これは制約だが、**同時に利点でもある**: 汎用 LLM に「markdown を保って」と
頼む方式は確率的に失敗するが、分割方式は決定的に正しい。

### 6.1 markdown（README.md）

#### 渡すもの / 渡さないもの

| 訳す | 訳さない（素通し） |
|---|---|
| 段落の本文 | フェンスドコードブロック（<code>```</code>）、字下げコードブロック |
| 見出しの文字列（`#` の後ろ） | YAML フロントマター、HTML ブロック |
| リスト項目の本文（記号の後ろ） | インラインコード <code>\`...\`</code> |
| 表のセル | URL、オートリンク、参照定義 |
| 引用の本文（`>` の後ろ） | バッジ（画像リンク）、アンカー |
| 画像の alt、リンクのテキスト | リンクの URL 部分 |

#### 難所はインラインコードを含む段落 → **実測では難所でなかった**

段落の途中に <code>\`dired-mode-map\`</code> が挟まる形が一番多い。
当初は 3 つの手を想定していたが、**実測（§4.3）で話が変わった。**

| | 手 | 当初の評価 | 実測後 |
|---|---|---|---|
| 1 | コードの前後で段落を切って散文だけ訳す | 駄目。文が分断される | 同じ。採らない |
| 2 | プレースホルダ（`⟦1⟧` など）に置換して後で戻す | 使えるが壊れうる。**`<\|plamo:` 系は使えない**（テンプレートが弾く） | **不要** |
| 3 | バッククォートごと渡し、同じ語を `glossary` に恒等写像で積む | **本線** | **glossary が不要。** 有無で出力が変わらなかった |
| **4** | **バッククォートごとそのまま渡すだけ** | — | **これが正解。** 132 種の識別子が 2b で全部、0.8b で 131/132 残った |

**モデルは記法と識別子を勝手に素通しする。** 翻訳特化モデルなので
「訳すべきでないもの」の判断が既に学習されているらしい。

**ただし検証は必ず付ける。** 0.8b は 1 件だけ
`` `dired+` `` → 「dired+」とバッククォートを壊した。訳文に識別子が元と
同じ回数現れたかを数え、合わなければ**その段落は原文のまま残す**。
**比較は `string-search` で行う**（§4.5-3 の罠）。

#### 【重要】見出しを訳すと目次のアンカーが壊れる（実測）

→ §4.5-1。**見出しに原文を併記する**（`# 貢献しよう！ (Contribute!)`）のが
いちばん安い。目次行自体は「単独のリンクだから訳さない」で素通しされるので、
アンカーは原文側から生成されてリンクが生きる。

#### 表は「訳したあとに桁を取り直す」

この設定は East Asian Width に手を入れている（`site-lisp/eaw.el`、
[docs](../japanese/eaw-and-cp5022x.md)）。**訳文は表示桁が原文と全く変わる**ので、
セルを訳したら区切り行を含めて整形し直す。桁の計算は `length` ではなく
**`string-width`**。

#### 【重要】訳した段落を折り返して保存してはいけない

GFM は段落内の単独改行をソフトブレイク = **空白 1 個**として描画する。
日本語の文の途中で改行すると、**レンダラによって文字の間に空白が入る。**
`fill-column` に合わせて整形したくなるが、**訳文は 1 段落 1 行のまま置く。**

### 6.2 help バッファ（`describe-function` / `describe-mode`）

#### 【重要】`*Help*` の本文を訳文で差し替えてはいけない

help バッファは**テキストプロパティの集合体**で、本文を入れ替えると全部消える。

- `help-xref` ボタン（シンボル・ファイル・変数へのリンク）
- 引数名に乗る `help-argument-name` face
- `help-mode-revert-buffer` が前提にしている元テキスト

さらに docstring には訳してはいけないものが詰まっている。

| | 扱い |
|---|---|
| 大文字の引数名（`BUFFER` / `NOERROR`） | **訳さない。** `glossary` に恒等写像で積む |
| `` `symbol' `` → `'symbol'` | 訳さない。リンクになっている |
| キー列（`C-c C-c`） | 訳さない |
| `\\[command]` / `\\{keymap}` | `substitute-command-keys` の展開後を見る |
| `(fn ARG...)` 行 | 訳さない |

#### 採る形は 3 択で、下 2 つが安全

| | 方式 | 評価 |
|---|---|---|
| 1 | `*Help*` の本文を置換 | **採らない。** リンクが全滅する |
| 2 | 元の `*Help*` の**末尾に訳を追記** | 安全。ボタンは無傷。`g` で消えるが、それは期待どおり |
| 3 | 別バッファに「原文と訳文の対」を出す | **最も安全。** 元に一切触らない |

**3 から入って、気に入れば 2 を足す**のが順序としてよい。

`describe-mode` は**キーバインド表が本文の大半**で、そこを訳す意味は無い。
散文だけに絞る。なおキーバインドを読むなら、この設定には既に
`<f1> b` の一覧表がある（[docs](../help/keyhelp.md)）。

### 6.3 ソースコメント

**ここが一番素直で、価値が高い。**

- tree-sitter の `(comment)` ノードを `treesit-query-capture` で正確に取れる。
  **正規表現で「コメントらしい行」を探す必要が無い**（文字列リテラル中の
  `//` を誤認しない）
- コメント記号（`//` / `#` / `;;` / `/* */`）と字下げを剥がして本文だけ訳し、
  戻すときに同じ記号と字下げを付ける
- 複数行コメントは**まとめて 1 つの入力にする**（行ごとに切ると文が分断される）
- **既定はバッファを書き換えず overlay で見せる。** 他人のリポジトリを
  読んでいる最中に差分を作らない（§5.4）
- `after-string` の overlay なら、元のバッファは完全に無傷

tree-sitter の文法が無い言語では静かに無効にする（この設定の既存方針。
[docs](../languages/tree-sitter.md)）。

### 6.4 `context` と `glossary` を活かす

PFML3 の機能をそのまま使える場面。

- **`context`**: 直前の段落を渡すと代名詞と専門用語の解釈が安定する。
  モデルカードの例（`The bank was muddy.` → 川岸）がまさにこれ
- **`glossary`**: ①識別子の恒等写像（§6.1）、②プロジェクト固有の訳語統一。
  後者はリポジトリごとに `.dir-locals.el` か専用ファイルで持てる
- **`form`**: 技術文書なので `plain`（常体）が既定として自然
- **対訳履歴**: 同じ文書内で訳語を揃えるのに効く。ただし毎回積むぶん
  プロンプトが伸びる。入力側は速いので（§4）払ってよいコスト

## 9. 次の一手

### Phase 0: 完了（2026-11-05）

やったこと: Vulkan ビルド済み zip（36 MB）+ 0.8b（0.53 GB）+ 2b（1.68 GB）を取得し、
`llama-bench` と `/completion` で測り、**実際の README 645 行を分割方式で全訳**して
構造の保持を検証。`GGML_VK_DISABLE_COOPMAT=1` を発見し、207 秒の耐久確認。

**結論: 実装に進んでよい。** 当初の見積もりは速度についてはよく当たっており、
**設計（常駐サーバ + HTTP + 段落分割）を変える必要は無い。**

成果物の置き場:

| | |
|---|---|
| llama.cpp | `~/.local/opt/llama.cpp-b12125-vulkan/`（git 管理外） |
| モデル | `~/.local/share/plamo-models/`（git 管理外） |
| 検証スクリプト | `tmp/plamo-probe/probe.ps1`（PFML3 の機能確認）/ `segment.ps1`（分割 + 検証）。**`tmp/` は git 管理外** |

再現コマンド:

```sh
# サーバ（0.8b を対話用に 18080、2b を文書用に 18081）
GGML_VK_DISABLE_COOPMAT=1 llama-server.exe \
  -m ~/.local/share/plamo-models/plamo-3-translate-0.8b-Q4_K_M.gguf \
  --port 18080 --host 127.0.0.1 -ngl 99 -c 4096 --parallel 1 --no-webui

# 分割翻訳（PowerShell）
pwsh -File tmp/plamo-probe/segment.ps1 -In <README.md> -Out <out.md> -Port 18080
```
