# 段階 2b — キャッシュと並列先読み

作成: 2026-09-03 / 状態: **実装・検証済み**

段階 2a（素通しプロキシ）で `magit-refresh-buffer` は 1.7 秒 → 0.6 秒になった。
残りの 0.6 秒はほぼ全部が **29 回の git 起動を直列に待っている時間**である
（1 回 20 ms × 29）。2b はこれを

- **並列化**（8 スレッドなら 29 コマンドが 180 ms で終わる）
- **キャッシュ**（変化していなければ 0 回）
- **先読み**（変化を検知した時点で走らせ、`g` を押した時にはもう答えがある）

の 3 つで潰す。目標は **数十 ms**。

---

## 1. いちばん難しいのはキャッシュの正しさ

速くするだけなら簡単だが、**古い答えを返すキャッシュは静かに壊れる**。
magit が事実と違う内容を表示し、しかもユーザはそれに気づけない。
2a で「唯一こわいのは静かに壊れること」と書いたのと同じ問題が、2b では
はるかに現実的な形で出てくる。

### 1.1 採らなかった案: 世代カウンタ + 無効化通知

デーモンがリポジトリごとに世代番号を持ち、Emacs が変化のたびに
`repo/invalidate` を送って世代を上げる、という案を最初に考えた。**破棄した。**

- 「Emacs が変化を漏れなく通知する」ことが正しさの前提になる。
  通知を 1 つ落とすと、そのリポジトリのキャッシュは**永久に**古いままになる
- 通知を漏らさないためには w32notify のイベント 1 件ごとに 1 通送ることになる。
  ビルド中は数千件になり、濃縮のために作った仕組み（段階 1）を台無しにする

### 1.2 採った案: トークンをリクエストに載せる

**キャッシュのキーに、Emacs が持っている「リポジトリ状態の通し番号」を含める。**

```
git/run { ..., repo: "<root>", token: 4711, role: "cache" }
```

デーモンは `(repo, token, コマンド)` でキャッシュする。トークンが違えば
問答無用でミスになる。**無効化通知は存在しない。**

これで正しさの条件が「通知が届くこと」から
**「トークンが古い状態を指し続けないこと」**に変わる。後者は Emacs 側だけで
閉じており、`my-magit-watch` が既に持っている情報で満たせる。

トークン（`my:magit-watch-repo-serial`）を上げるのは 2 か所だけ:

| いつ | なぜ |
|---|---|
| 分類を通った w32notify イベント 1 件ごと | ワークツリー / index / HEAD の変化 |
| `magit-pre-refresh-hook` | **magit 自身の書き込み**。stage / commit / checkout など。`magit-refresh` は magit のコマンドの後に必ず走る |

後者が効くのが重要で、`magit-run-git-with-input`（`call-process-region`）や
`magit-start-process`（非同期）はデーモンを通らないため、
デーモン側では書き込みを観測できない。しかし magit はコマンドの後に必ず
`magit-refresh` を呼び、そこで `magit-pre-refresh-hook` が走る。
**`g` を押したときも同じ**なので、「`g` は必ず本当のことを言う」が保証される。

### 1.3 監視が動いていなければキャッシュも動かない

`repo` / `token` は `my:magit-watch` が監視しているリポジトリでしか付かない。
付いていなければ `role` は nil になり、デーモンは 2a と同じ素通しになる。

- `M-x my:magit-watch-mode` で監視を切ると、キャッシュも自動的に無効になる
- 監視していないリポジトリ（`magit-mode-hook` 前の `magit-toplevel` など）も同じ

**キャッシュの寿命は監視の寿命に従属する。** これが最大の安全弁。

### 1.4 それでも残る穴

w32notify のイベントは落ちる（段階 1 で実測: 1000 ファイルに対し 4095/10000）。
落ちればトークンは上がらず、キャッシュは古いままになる。

- バーストの中で全イベントが落ちることは考えにくい（1 件でも残れば上がる）
- **`g` を押せば必ず上がる**（1.2）。ユーザ側の逃げ道が常にある

## 2. `update-index --refresh` の扱い（prelude）

`magit-status-refresh-buffer` は**先頭で** `git update-index --refresh` を呼ぶ。
これは「stat は変わったが内容は同じ」ファイルのインデックス側 stat キャッシュを
更新するもので、**成功するとインデックスを書く**。

先読みでこれを飛ばすと、こうなる:

1. 先読みが `diff-files` などを実行 → 「変更あり」と出る（stat が古いだけ）
2. magit が本物の `update-index --refresh` を実行 → インデックスが直る
3. magit が `diff-files` を要求 → **1 のキャッシュが返る** → 変更が無いのに
   変更ありと表示される

そこで **`role: "prelude"`** を導入する。Emacs が明示的にそう指定した
コマンドだけを、デーモンは先読みの先頭で（直列に）実行する。
キャッシュはしない。

対象は `update-index --refresh` **ただ 1 つ**。デーモンは相変わらず git の
意味を知らず、Emacs が指定したことをやるだけである（2a の設計上の約束を守る）。

### 副作用と、それが自動的に収束すること

先読みの `update-index --refresh` がインデックスを書くと w32notify の
イベントが出て、トークンが上がり、**いま作ったキャッシュが無効になる**。
一見まずいが、そうはならない:

- 本当に編集されたファイルは stat キャッシュが更新されないので**書かない**
  （＝ 普通のケースでは何も起きない）
- 書いたということは状態が変わったということなので、取り直すのが正しい
- イベントはデバウンスのタイマーを**張り直す**ので、先読みも張り直される（3 章）

## 3. 二段タイマー — 先読みをいつ頼むか

段階 1 のデバウンスは 0.4 秒。ここに**先読み用の短いタイマー 0.1 秒**を足す。
どちらも w32notify のイベントごとに張り直す。

```
      イベント群 ...........|
                            |--0.1s--> 先読みを頼む (repo/prewarm)
                            |------------0.4s------> リフレッシュ
```

- バーストが終わって 0.1 秒でトークンが安定する。その時点で先読みを頼めば
  **300 ms の頭金**ができ、リフレッシュ時にはキャッシュが埋まっている
- ビルド中は 0.1 秒の隙間ができるまで発火しない。発火しても
  `my:magit-watch--stale-p`（＝ `.gitignore` 判定込み）を通すので、
  **無視されるだけの変化では先読みも走らない**
- 判定は段階 1 の実装をそのまま使う。先読み側では `pending` を消さない

**先読みの発火は純粋な最適化**である。落としても遅くなるだけで、
リフレッシュ直前にもう一度頼むので必ず追いつく。

### 1 ファイル保存で 10 件のイベントが出ることへの対応

段階 1 の実測どおり、1 ファイルの保存で w32notify は約 10 件のイベントを出す。
トークンは 1 件ごとに上がるので、**最初のイベントで先読みを頼むと
残り 9 件で無効化される**。0.1 秒待つのはこのため。

## 4. デーモン側の構造

### 4.1 単発実行の共有 (single-flight)

同じキーの実行が同時に 2 つ走らないようにする。先読みが走っている最中に
Emacs が同じコマンドを要求したら、**新しく git を起動せずに待ち合わせる**。

これがあるので、先読みが間に合わなくても損をしない。
`g` を押した瞬間に先読みを頼み、そのまま magit が順に要求しても、
実際の待ち時間は「直列 29 回」ではなく「並列 1 回ぶん」になる。

| | 先読みなし | 先読みが間に合った |
|---|---|---|
| 2a | 580 ms | — |
| 2b | 約 200 ms（prelude + 並列） | **数十 ms** |

### 4.2 レシピの学習

先読みで何を走らせるかは**デーモンが観測して覚える**。magit の内部を
デーモンが知る必要はない。

- `role: "cache"` で来たコマンドを `observed` に順に記録（キーで重複除去）
- `repo/prewarm` を受けたら、`observed` が空でなければ `recipe` に移して空にする

`repo/prewarm` はリフレッシュの**直前**に来るので、`observed` にはその時点で
**直前のリフレッシュで実際に使われたコマンド列**が入っている。
これをそのまま次回の先読みに使う。状態が変わってコマンド列が変われば、
次の周で自動的に追随する。

### 4.3 並列度

`available_parallelism()` を上限 8 で丸める。29 コマンドなら 4 波。

### 4.4 状態

```
repo -> {
  token,                  // いまキャッシュしている世代
  cache:    key -> 結果,   // token が変われば捨てる
  inflight: key -> Job,   // single-flight
  observed, recipe, prelude,
  prewarming, dirty,      // 先読みの多重起動を防ぐ
  hits, misses,
}
```

`repo/forget` で丸ごと捨てる（監視をやめたとき）。

## 5. プロトコル (v2)

```
initialize                -> { protocol: 2, version, pid, threads }
env/register { id, env }  -> { ok }
git/run { program, cwd, args, env, want_stderr,
          repo?, token?, role? }
     role: "cache"   キャッシュしてよい読み取り
           "prelude" 先読みの先頭で直列に走らせる。キャッシュしない
           なし      素通し。キャッシュにも先読みにも関与しない
     -> { exit, stdout(b64), stderr(b64|null), elapsed_ms, cached }
repo/prewarm { repo, token }   通知。先読みを開始する
repo/forget  { repo }          通知。状態を捨てる
gitd/stats                -> { repos: [...] }   デバッグ用
shutdown                  -> { ok }
```

`repo` / `token` / `role` が無ければ 2a と完全に同じ動作になる。

## 6. Emacs 側の変更

### `my-gitd.el`

- `my:gitd--role`: `update-index --refresh` は `prelude`、
  `my:gitd-read-only-p` が真なら `cache`、それ以外は nil
- `repo` / `token` は `my:magit-watch-scope` から取る。**git は呼ばない**
  （`magit-toplevel` を呼ぶと `magit-process-file` に再入する）
- `my:gitd-prewarm` / `my:gitd-forget` を公開
- 統計にキャッシュヒット率を足す

### `my-magit-watch.el`

- リポジトリ構造体に `serial` を足し、分類を通ったイベントごとに 1 増やす
- `my:magit-watch-scope` を公開（`(ROOT . TOKEN)` を返す）
- 先読み用タイマー（0.1 秒）を足す
- `magit-pre-refresh-hook` で `serial` を上げて先読みを頼む

## 8. やらないこと（2c 送り）

**監視そのものの Rust 移行は今回やらない。**

当初の構想では 2b で監視をデーモンに移し、`.gitignore` の判定を
`ignore` crate に置き換えるつもりだった。分けた理由:

- 速度の目標（0.6 秒 → 数十 ms）は**キャッシュと並列化だけで達成できる**。
  監視の移行はそこに寄与しない
- `check-ignore` は段階 1 でキャッシュ済みで、**定常状態では 0 回**しか
  呼ばれない。`ignore` crate に置き換えても速度は変わらない
- 監視は段階 1 で実測して作った部分であり、キャッシュの正しさと
  同時に動かすと、問題が起きたときにどちらが原因か切り分けられない

2c で移す価値があるのは次の 2 点で、どちらも速度とは別の話:

- macOS / Linux 対応（`subtree` 相当が inotify / kqueue に無い）
- `ReadDirectoryChangesW` のバッファ溢れを**検知**できるようになる
  （Win32 API は溢れを通知するが、Emacs の `w32notify` はそれを渡さない）。
  溢れを検知できればトークンを強制的に上げられ、1.4 の穴が塞がる

## 9. 実装結果 (2026-09-03)

### 9.1 実測 (`~/.emacs.d`、`magit-refresh-buffer` 1 回)

| | 時間 | Emacs からの git 起動 | デーモンでの git 起動 |
|---|---|---|---|
| 段階 0 (デーモン無し) | 1503 / 1544 ms | 28 | — |
| 段階 2a (素通し) | 683 / 672 ms | 0 | 28 |
| **2b: 変化なし** | **56 / 54 ms** | 0 | **0** |
| **2b: 0.3 秒前に先読み** | **72 / 54 ms** | 0 | 0 |
| 2b: 直前に先読み (`g` 相当) | 208 ms | 0 | 28 (並列) |
| 2b: 先読み無し | 667 ms | 0 | 28 (直列) |

**当初の 1.7 秒が 50〜70 ms になった。** 28 コマンド中 27 がキャッシュから返り、
残る 1 は prelude (`update-index --refresh`) で、これは意図的にキャッシュしない。

残った 50 ms はほぼ magit 自身の Elisp (セクションの構築と描画) で、
stdio の往復は 28 回で合計 4 ms 程度。ここから先はデーモンでは縮まない。

GUI での実地計測 (外部からファイルを変更 → 自動更新):

| | |
|---|---|
| 自動リフレッシュ 1 回 | **51〜81 ms** (3 回連続で再現) |
| 外部でのブランチ切り替え | 262 ms (meta なのでキャッシュが飛ぶ。正しい) |

### 9.2 【実装中に見つけた】先読みが自分自身を呼び続ける

最初の GUI 検証で **自動リフレッシュが 1 回も走らなかった**。先読みは 63 回
走っているのにリフレッシュ 0 回、という形で表面化した。

原因は「**読み取りだけの git もファイル変更イベントを出す**」こと。実測:

| コマンド | イベント | 内訳 |
|---|---|---|
| `update-index --refresh` (何もしない場合でも) | 3 | `.git` ×1 / `.git\index.lock` ×2 |
| `status --porcelain` | 4 | `.git` ×2 / `.git\index.lock` ×2 |
| `diff-files -z --name-only` | 1 | `.git` ×1 |
| `rev-parse HEAD` / `for-each-ref` | 0 | — |
| 読み取り 10 種をまとめて | 4 | `.git` ×2 / `.git\index.lock` ×2 |

`status` ですら index.lock を作る。したがって先読み (28 コマンド) は必ず
イベントを出し、それがデバウンスのタイマーを張り直し、0.1 秒後にまた
先読みが走る。**リフレッシュの 0.4 秒はいつまでも来ない。**

3 つ直した。分類上これらはすべて `suspect` なので、そこを狙い撃ちできる。

1. **`suspect` はトークンを進めない。** 進めると自分のリフレッシュや先読みが
   自分のキャッシュを壊す。決め手のイベントが落ちた場合は
   `my:magit-watch--fire` がフィンガープリントの不一致を見て進めるので、
   段階 1 の「イベントは落ちる」への備えは残る
2. **`suspect` は既に張ってあるタイマーを延長しない。** 「何かが起きたかも」
   以上のことを言わないので、評価が予約済みなら足す情報が無い
3. **1 つの窓では先読みを 1 回しか頼まない**（Emacs 側）。さらにデーモン側でも
   **レシピが全部キャッシュ済みなら先読みごと打ち切る**。これが無いと
   prelude だけが毎回走ってイベントを出し続ける

### 9.3 【実装中に見つけた】`default-directory` の `~` を展開していなかった

`git.exe の起動に失敗 (cwd=~/.emacs.d/gitd/target-dev/release/):
ディレクトリ名が無効です。 (os error 267)`

Emacs は file バッファの `default-directory` を `~/...` に略記することがある。
`call-process` は内部で `expand-file-name` するが、**Rust の `current_dir` は
`~` を展開しない**。`my:gitd--request` で `expand-file-name` してから渡す。

**これは段階 2a から入っていたバグ**で、たまたま magit のバッファからしか
呼ばれていなかったので表に出ていなかった。

### 9.4 `magit-process-record-invocations` は素通しにする

magit には全 git 呼び出しをログに残すデバッグ機能があるが、その処理は
`magit-process-file` の**本体**にある。`:around` で横取りして `orig` を
呼ばない以上、有効にしても記録されない。

有効なときはルーティングしないようにした。デバッグ中だけ遅くなるが、
magit から見た挙動が完全に保たれる。

（同じ理由で、`magit-process-file` に後から足した advice も呼ばれない。
テストを書くときは `my:gitd-mode` を有効にした**後**に足すこと。）

### 9.5 読み取り一覧に足したもの

リフレッシュ 1 回の 28 コマンドを実際に並べて確認した (`probe-roles`)。
`magit-staged-files` / `magit-unstaged-files` が使うプルーミングが
抜けていたので足した。

```
diff-index / diff-files / diff-tree / worktree (list のみ)
```

なお表示上サブコマンドが欠けて見えることがあるが、これは magit が
`--literal-pathspecs' を受け付けないコマンドのために
`magit-git-global-arguments' を let で短くしているためで、
呼び出し時点の判定は正しい。

### 9.6 検証

- `probe-2b` (batch): 25 項目。役割判定・キャッシュの効き・
  **トークンを進めなければ古い答えが返ること**・書き込みでトークンが進むこと・
  先読み・打ち切り・`repo/forget`・シャドウモード
- `probe-gui-2b` (GUI): 外部変更での自動更新 / `.gitignore` されたビルド出力を
  無視すること / レシピ学習後の速さ / `g` / stage・unstage・commit /
  シャドウモード / 外部でのブランチ切り替え。3 回連続で全項目 PASS
- **シャドウモードはキャッシュヒットも素の `process-file` と突き合わせる。**
  古い答えを返していれば必ず不一致として出る。全実行で不一致 0
